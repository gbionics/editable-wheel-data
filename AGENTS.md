# Maintainer and agent guide

## Purpose and scope

This repository implements the standalone PEP 517/660 backend wrapper proposed in
https://github.com/gbionics/resolve-robotics-uri-py/issues/25 and the supplied
`editable-wheel-data-discussion(1).zip`. The archive is reference input, not a
package dependency or distribution asset. Keep README.md lean and human oriented;
put implementation detail and future maintenance guidance here.

The first supported delegates are setuptools and Hatchling. Test both with pip
and uv as frontends. Do not hard-code a backend whitelist: other PEP 660 delegates
may work, but compatibility claims need integration evidence. Native backend
rebuild mechanisms, scripts, headers, and arbitrary generated build outputs are
outside the initial scope. Only `.data/data/` external resources are transformed.

## Configuration contract

Consumers list this wrapper and their delegate in `build-system.requires`, select
`build-backend = "editable_wheel_data"`, and set `[tool.editable-wheel-data]`'s
`backend` to the delegate. All source mappings come from the delegate's own data
configuration. The former `files` option is removed and must be rejected as an
unknown setting, including empty tables. There is no separate override or fallback
mapping mechanism. Payload-equality checks always apply to existing wheel data.
Ordinary wheels and their settings remain delegated unchanged.

- `hatchling.build`: read `[tool.hatch.build.targets.wheel.shared-data]` in
  pyproject.toml after the build. Sources map to exact file destinations or
  recursively expanded directory destinations. hatch.toml and mappings added
  only by custom Hatchling hooks remain unsupported; generated sources named in
  the static table are supported if they survive the build.
- `setuptools.build_meta` and `setuptools.build_meta:__legacy__`: observe the
  Distribution returned by public `setuptools.setup()` during the delegated
  editable build, using `_setuptools.py`. This covers data_files from setup.py,
  setup.cfg, and pyproject.toml, after setuptools has resolved globs and dynamic
  configuration. Do not maintain a parallel parser for setuptools tables.
  Temporarily wrap setup(), preserve its arguments and return object, record
  distributions after setup() completes, and restore the original function in a
  finally block. Use the last returned distribution (the outer setup call).
  Do not execute setup.py again to discover data or read private global state.
  PEP 517/660 frontend hooks run in isolated subprocesses; concurrent builds in
  the same backend process are not supported by this observation mechanism.
  If the delegate never calls setuptools.setup(), fail clearly rather than
  silently dropping dynamic data. Code using only distutils.core.setup() is not
  covered by this adapter.

Setuptools data_files supply destination directories and source lists, not exact
renamed destinations. Keep source basenames and one-to-many mappings; deduplicate
identical source/destination pairs. Bare source-file entries target the data-prefix
root. Normalize native paths from Python collectors, and accept absolute source
paths only if their resolved files remain inside the project. Reject directories
as setuptools data_files sources. A generated ament marker under the checkout's
build/ directory is durable and valid; an output in a deleted temporary build tree
is not.

`include-package-data = true` in `[tool.setuptools]` affects package-internal
resources, independently of external data_files. Preserve it and all other package
resource settings through delegation. The wrapper must not turn package_data or
MANIFEST.in entries into external share mappings. Setuptools' editable import
mechanism makes internal resources available; only external `.data/data/` resources
are rewritten and activated by this package. Keep the normal-wheel internal data
copies intact.

Unrecognized delegates yield no mappings; unmapped data in a returned editable
wheel fails with a hint to use a supported backend configuration. Do not infer
original source locations from wheel payloads alone. Consumers must include data
needed in their sdists through the original backend's own configuration.

Use relative POSIX paths on every platform. Reject traversal, absolute paths,
Windows drives, backslashes, NULs, missing sources, unknown settings, non-string
values, destination duplicates (case-insensitively), and file/directory destination
conflicts. Resolve source files and reject links escaping the project. Directory
symlinks are not traversed by recursive discovery. Files generated by a delegate
can be mapped if they exist after build_editable returns and remain durable.
New/deleted/renamed files, moved checkouts, and changed mappings require reinstall.

## Architecture and invariants

- `src/editable_wheel_data/__init__.py` reads wrapper configuration from the frontend's
  working directory, resolves the delegate, and exposes standard PEP 517/660 hooks
  dynamically. Preserve missing optional hooks with AttributeError; do not add
  unconditional callable stubs for metadata or editable hooks. Some frontends
  intentionally fall back to building wheels when metadata hooks are absent.
  Reject direct recursive delegation and malformed backend object paths.
- Ordinary wheel, sdist, requirements, and metadata hooks are forwarded unchanged,
  including caller arguments and return values. Python import editability remains
  entirely the delegate's responsibility. Do not add runtime dependencies to
  editable metadata or modify the delegate's dist-info metadata.
- The editable build delegates first, then expands mappings (allowing durable
  generated sources) and rewrites the returned wheel. Never guess the target
  environment from the build interpreter's prefix: build isolation and frontend
  uninstall ordering make that unreliable.
- `_wheel.py` finds one dist-info directory, adds mapped data copies and an embedded
  standard-library runtime module plus `.pth` activation import. Helper names are
  derived from the normalized distribution/version plus a fingerprint of the
  runtime source and mapping manifest. This prevents rapid same-version reinstalls
  from reusing stale .pyc files when helper size and timestamp happen to match. Reject duplicate or unsafe
  ZIP paths, signed wheels, unmapped external data, mismatched discovered payloads,
  and helper-name collisions. All changes are staged and atomically replace the
  original wheel. Preserve delegate ZIP metadata, especially executable modes.
- Regenerate RECORD with URL-safe, unpadded SHA-256 digests and byte lengths; RECORD
  itself has empty digest/length. Data paths stay in RECORD so frontend uninstall
  owns the eventual links. Removing recorded data or creating unrecorded links
  breaks lifecycle behavior. ZIP symlink attributes alone do not implement this
  feature with standard frontends.
- `_runtime.py` is copied into each editable wheel. It must remain standard-library
  only and compatible with Python 3.9. Its installed `__file__` locates the matching
  dist-info directory through PathDistribution, avoiding another installation of
  the same name elsewhere on sys.path. Installed RECORD suffix matches locate the
  frontend's actual data destinations; ambiguity must fail explicitly.
- Runtime activation checks source existence, accepts already-correct links,
  rejects unrelated links and modified installed copies, and uses a unique
  temporary symlink plus os.replace. Always clean temporary links after failure.
  Source edits between build and activation are valid: compare the installed copy
  to its build-time hash, not to current source bytes.

## Activation and limitations

A standard backend has no post-install hook. Symlinks activate on the next normal
Python startup after installation. External tools see copies until that happens;
`python -c "pass"` triggers activation. `python -S` does not. This behavior is a
public contract and must remain visible in the README. Python site processing
prints helper failures to stderr but may still exit successfully; tests must check
stderr as well as process exit status. Do not claim synchronous activation.

The wrapper is a build dependency only. Editable consumers must work without it
installed at runtime. Ordinary wheels include no activation helper. Source checkout
lifetime is required; a missing source reports an actionable reinstall error.
Windows needs Developer Mode or symlink privileges; report failures, never silently
fall back to non-editable copies. Tested CI runners must actually permit symlinks.

Shared destination ownership across distributions is unsupported; use distinct
paths. RECORD suffix ambiguity is rejected rather than guessed. Custom user,
prefix, and target schemes are not in the supported test matrix. Concurrency,
backend-specific generated artifacts, performance at very large mapping sizes,
and broader install-scheme support need additional evidence before claims change.
The wrapper deliberately does not manage directories as symlinks: individual
recorded files preserve uninstall behavior.

## Development and verification

The default Pixi environment uses Python 3.12, installs this package editable, and
reuses the existing `project.optional-dependencies.test` as a Pixi feature. Run
`pixi run test` for the full suite, or `pixi run --locked test` to enforce the
committed `pixi.lock`. The lock covers Linux x86_64/ARM64, macOS Intel/ARM64, and
Windows x86_64; only the host platform is installed locally. Regenerate the lock
with `pixi lock` after dependency or manifest changes. The lock fixes the development
environment; isolated consumer builds in integration tests still fetch their
configured build requirements from the package index. Keep `.pixi/` ignored and
include `pixi.lock` in sdists so the documented development command also works
from a source distribution. CI still installs the built wheel to test artifacts
across its Python-version matrix.

The equivalent pip-based development commands remain available:

```sh
python -m pip install -e '.[test]'
python -m pytest -q
python -m build
python -m twine check dist/*
```

Tests are under `tests/`. Unit tests cover delegation and optional-hook absence,
configuration/path/collision validation, backend-table discovery,
wheel integrity, executable modes, runtime
activation, missing sources, user edits, unrelated links, ambiguous RECORD paths,
and simulated missing symlink privileges. Integration tests build a local wrapper
wheel, supply it via PIP_FIND_LINKS/UV_FIND_LINKS to isolated consumer builds, and
create temporary venvs. They require network access to the configured package
index and a `uv` executable (included in the test extra). Each combination of pip
or uv and setuptools or Hatchling tests normal wheel data, first activation,
live edits, editable reinstall, replacement with ordinary copies, and uninstall
cleanup without deleting source data. Consumers must not import the wrapper at
runtime. The lifecycle fixtures use only backend data tables, proving automatic
discovery with no duplicate mapping configuration. Unit tests cover rejection of
the removed files option, directory expansion, multiple destinations, validation,
collisions, and sources generated during builds. Setuptools adapter unit tests
cover setup() observation and restoration (including failures), native/absolute
source normalization, duplicate mappings, and one-to-many destinations. Integration
tests cover resolved globs and setup.cfg in addition to static pyproject data.
A separate test rebuilds this package's wheel from its sdist, including
the embedded runtime source. Inspect startup stderr for `Error processing line`.


Minimal test projects live directly under `tests/fixtures/`:

- `hatchling/` exercises recursive shared-data with nested paths and spaces.
- `setuptools_dynamic/` exercises a setup.py data_files collector, package.xml,
  a generated ament marker, and include-package-data = true. Its MANIFEST.in
  selects an internal JSON resource to test normal-wheel inclusion and editable
  access through importlib.resources.

Keep fixtures self-contained and limited to the files needed by their tests;
do not vendor external example repositories, documentation, or provenance files.
Tests copy the projects unchanged into temporary source paths with spaces. Both
projects run through pip and uv, checking ordinary wheels, editable reinstall,
live edits, uninstall cleanup, and restoration of ordinary copies.

Use tests appropriate to changes. Keep install lifecycle coverage meaningful;
checking only generated wheel contents cannot establish correct pip/uv behavior.
When testing artifacts, import the built distribution rather than relying on a
source PYTHONPATH. Version/platform claims should distinguish local results from
configured CI coverage. CI targets Python 3.9, 3.12, and 3.14 on Linux, macOS, and
Windows; configured matrix entries are not evidence of passed runs.

For the initial implementation, the workspace's system Python lacked pip. A local
venv can use the existing Pixi Python or another interpreter with ensurepip. Use a
writable uv cache (e.g. under /tmp) within restricted filesystem environments.
Do not commit environments, build artifacts, caches, or the supplied ZIP attachment.

## Packaging and releases

The package itself uses Hatchling, src layout, Python >=3.9, and conditional tomli
for Python <3.11. Keep the runtime helper compatible with the full supported
Python range. The BSD-3-Clause LICENSE already belongs to this repository.
`pyproject.toml` explicitly includes sources, tests, README, LICENSE, this guide,
and workflow files in sdists; wheel contents remain the package plus metadata.

`.github/workflows/build.yml` follows the build/test/artifact/publish pattern of
https://github.com/gbionics/mujoco-robotics-uri. This is pure Python: build one
universal wheel and sdist, without native wheel matrices or auditwheel. Check
artifacts with twine, install the built wheel with its test extra in the test
matrix, then publish those exact artifacts only after build and all tests pass.

The user has configured a pending PyPI Trusted Publisher with:

- Project: editable-wheel-data
- Repository: gbionics/editable-wheel-data
- Workflow: build.yml
- Environment: pypi

Keep those names consistent. Publishing is triggered only by a published GitHub
release. Its tag must equal `project.version`, optionally with `v` prepended.
Publishing uses pypa/gh-action-pypi-publish and job-scoped `id-token: write` in the
`pypi` environment; no API token is needed. Build/test jobs have read-only repository
permissions. Do not publish an editable consumer wheel as a release artifact.

User-requested implementation work does not itself request an actual release;
prepare and validate the workflow without creating a release or uploading to PyPI.
For GitHub reads, `gh` is available. The connected GitHub plugin initially returned
an organization SAML restriction; the linked public issue was successfully read
using the public API with network access.

Workflow action versions were checked against each repository's latest stable
GitHub release on 2026-11-02: checkout v7.0.1, setup-python v7.1.0,
upload-artifact v7.0.2, download-artifact v8.0.2, and gh-action-pypi-publish
v1.14.3. Use explicit stable release tags when updating. Check upstream release
notes for major-version migrations; the upload/download pair keeps the default
archived-artifact format. These actions run on GitHub-hosted runners. Checkout's
new restrictions for pull_request_target/workflow_run do not affect the current
push/pull_request/workflow_dispatch/release triggers.
